## ADR-001

### タイトル

同一オリジン構成を採り CORS を実装しない

### 状態

採用

### 日付

2026-08-24

### 決定内容

フロントエンドと API を、開発時・本番時ともに同一オリジンに見せる。アプリケーションに CORS 設定 (`Access-Control-Allow-Origin` など) を実装しない。

* 開発: Angular 開発サーバの `proxy.conf.json` が `/api/*` を `http://localhost:8000` へ転送する。
* 本番: `web` コンテナの nginx が Angular の静的ファイルを配信し、`/api/*` を `api` コンテナへリバースプロキシする。

### 理由

* 認証を持たないため Cookie の送受信要件が無く、CORS を許可する動機が弱い。
* 同一オリジンに揃えれば、プリフライトの扱い・許可オリジンの環境別設定・本番で誤って `*` を許可する事故のいずれも発生しない。
* 開発と本番で URL 構造 (`/api/...`) が同一になり、フロントエンドに環境別のベース URL 設定が不要になる。

### 影響

* フロントエンドは API を**常に相対パス**で呼ぶ。絶対 URL のベースパスを持たせない。
* 結合テスト・受け入れテストは、`web` 経由の同一オリジン構成か API への直接アクセスのいずれかで行う。**CORS を前提にしたテストハーネスを組まない。**

### 関連文書

* `docs/P003-backend-spec.md` §2

## ADR-002

### タイトル

`sa` バイナリは `sadf` 経由で読む (自前パースしない)

### 状態

採用

### 日付

2026-08-24

### 決定内容

`saDD` バイナリの読み取りは、sysstat の `sadf` コマンドを `subprocess` で起動し、その JSON 出力 (`sadf -j -- -A`) を解釈する方式とする。バックエンドのコンテナイメージに sysstat を同梱する。

### 理由

* sysstat のバイナリ形式は**バージョン間で互換性が保証されておらず**、構造体定義がバージョンごとに変わる。自前パーサは採取元の sysstat バージョンが変わるたびに壊れる。
* `sadf` は sysstat 自身が提供する公式の変換手段であり、形式変更に追随している。

### 影響

* バックエンドコンテナに sysstat の導入が必須になる。
* `sadf` が無い環境では `sa` を読めない。ただし `sar` 経路は動作するため、アプリ全体は成立する (ADR-003)。
* `sa` ファイルを生成したホストと、コンテナ内 sysstat のバージョンが大きく異なると `sadf` が失敗しうる。この場合は `SADF_FAILED` (502) を返し、同一日の `sar` ファイルがあれば `hint` で案内する。
* **`sadf -j` の JSON フィールド名は、本設計時点で実出力による確認ができていない** (開発環境に `sadf` を導入できなかったため)。実環境での初回実行時に確認し、必要なら対応表を修正する。修正範囲を局所化するため、対応表は `app/metrics/catalog.py` の 1 箇所に集約する。

### 関連文書

* `docs/P001-requirement.md` §3.3(a) / `docs/P003-backend-spec.md` §9 / `docs/P005-impl-plan.md` §5

## ADR-003

### タイトル

`sar` テキストは自前解析し、両経路を共通の中間表現へ正規化する

### 状態

採用

### 日付

2026-08-24

### 決定内容

`sarDD` テキストは変換コマンドを介さずアプリケーション内で直接解析する。`sa` 経路 (`sadf`) と `sar` 経路 (テキスト解析) の双方を、**共通の中間表現 `RawTable` を経て同一の正規化関数**に通し、同一の API 応答スキーマへ落とす。

### 理由

* `sadf` はバイナリを入力とするツールであり、テキストの `sar` を入力にできない。形式を `sadf` 側に 1 本化する案は成立しない。
* `sar` のテキスト出力は人間可読な安定した書式であり、外部プロセスを起動する必要がない。sysstat が無い環境でも動作する。
* 中間表現を挟むことで、2 経路の差異をリーダ層の内部に閉じ込め、「両経路の結果が一致すること」を構造として担保できる。

### 影響

* 解析ロジックが 2 系統になる。両者の出力が同じ内部構造に揃っていることを、結合テスト (2 経路の一致) で担保する必要がある。
* **`sar` 解析の実装上の要点** (後続の実装担当が最も誤りやすい箇所):
  * 繰り返されるヘッダ行の直前には必ず空行が入る。**空行を「セクションの終わり」と解釈してはならない。**同一列構成のブロックは 1 グループとして連結する。
  * `Average:` で始まるブロックは期間平均であり、時系列サンプルから除外する。
  * 列は空白揃えで固定幅ではない。連続空白で分割する。

### 関連文書

* `docs/P001-requirement.md` §2.1(c) / `docs/P003-backend-spec.md` §7.2, §7.3, §8

## ADR-004

### タイトル

永続データストアを持たず、プロセス内メモリのみで状態を保持する

### 状態

採用

### 日付

2026-08-24

### 決定内容

RDB・KVS を導入しない。参照するデータはファイルシステム上のログファイルのみとし、ファイルカタログ (採取日) とメトリクス解析結果を**プロセス内メモリ**にキャッシュする。キャッシュの失効は `(パス, mtime, サイズ)` の一致で判定し、時間ベースの有効期限を設けない。

### 理由

* 本アプリは「ファイルを選んでグラフを見る」ものであり、取り込みバッチ・スキーマ移行・データ保持期間の管理を伴う構成は過剰である。
* ログファイルは読み取り専用であり、キャッシュはその派生物にすぎない。失っても再構築でき、内容が一意に定まる。

### 影響

* **マイグレーションが存在しない。**したがって非冪等なマイグレーションによる起動失敗は構造上発生しない。ただし再起動そのものの確認 (2 回目以降の起動、キャッシュ再構築) は受け入れテストで行う。
* 複数ワーカーで起動した場合、キャッシュはワーカーごとに独立する。整合性の問題は生じない。
* 複数ファイルを横断した集計はできない (本バージョンのスコープ外)。
* 将来データストアを導入する場合は、**バージョン管理テーブルによる差分適用方式**とすること。「全件再実行」方式は、後から `ALTER TABLE ... ADD COLUMN` が必要になった時点で破綻するため採用しない。

### 関連文書

* `docs/P002-frontend-spec.md` §6.1 / `docs/P003-backend-spec.md` §3, §4.1

## ADR-005

### タイトル

Angular + FastAPI を採用する

### 状態

採用

### 日付

2026-08-24

### 決定内容

フロントエンドに Angular (TypeScript)、バックエンドに Python + FastAPI を採用する。グラフ描画には **Chart.js を直接**用いる (`ng2-charts` は使わない)。

### 理由

* `require.txt` がフロントエンドに Angular、バックエンドに Python を指定しており、FastAPI は利用者が明示的に指定した。
* `sa`/`sar` の解析は外部コマンド呼び出しとテキスト処理が中心であり、Python の標準ライブラリで完結する。
* Pydantic による応答スキーマ定義が API 仕様の記述とそのまま一致し、OpenAPI が自動生成されるため Angular 側の型と齟齬が出にくい。

### 影響

* API 応答のフィールド名は **camelCase** で統一する (Pydantic モデルにも camelCase で直接定義する)。
* Angular のバージョンは **20 系**とする。当初 18 系を想定したが、開発環境の Node v24.12.0 を Angular 18 がサポートしないため。
* `ng2-charts` は採用しない。`ng2-charts@10` が Angular 22 以上を要求し Angular 20 と両立しないため、Chart.js を直接利用する。ラッパを外したことで `Chart` インスタンスの生成・破棄はコンポーネントが管理する。

### 関連文書

* `docs/P001-requirement.md` §3.1, §3.2 / `docs/P005-impl-plan.md` §1.2

## ADR-006

### タイトル

グラフの X 軸に線形軸を用いる (カテゴリ軸・時間軸を使わない)

### 状態

採用

### 日付

2026-08-24

### 決定内容

Chart.js の X 軸を `type: 'linear'` とし、X 値に epoch ミリ秒を与える。目盛りのラベルは `ticks.callback` で `HH:mm` に整形する。

### 理由

* **カテゴリ軸は、値の実際の間隔にかかわらず各点を等間隔に描画する。**本システムのサンプル間隔は実測で揺らぎ (00:10:09 / 00:20:12 / 00:30:03)、収集停止があれば大きな欠測が生じる。カテゴリ軸ではその欠測が視覚的に潰れ、連続して収集されていたかのように見えてしまう。性能ログの閲覧という用途では誤読を招く。
* 時間軸 (`type: 'time'`) は date adapter の追加依存を必要とする。本システムは 1 ファイル = 1 日分であり、目盛りを `HH:mm` で出せれば十分なため、追加依存の要らない線形軸で足りる。

### 影響

* データ点は `{x: number, y: number|null}` の形で与える。
* 目盛り位置が日時として最適化されず、切りの良い時刻に揃わないことがある (読み取りに支障はない)。
* API 契約は変わらない。`timestamps` は文字列のまま返し、フロントエンドで数値へ変換する。

### 関連文書

* `docs/P002-frontend-spec.md` §3.3 / `docs/P010-design-review.md` 矛盾点 #1 / `docs/P011-impact-analysis.md`

## ADR-007

### タイトル

ファイルは不透明な `fileId` 経由でのみアクセスする

### 状態

採用

### 日付

2026-08-24

### 決定内容

API はファイルパスを直接受け付けない。`fileId = base64url(ファイル名)` (パディング除去) を用い、解決時に**必ず次の順序**で検証する。

1. base64url として復号できるか
2. 復号結果が `^sar?[0-9]{2}$` に合致するか (**パス結合より前**)
3. ログディレクトリと結合
4. `realpath` がログディレクトリ直下か
5. 通常ファイルとして存在するか

失敗はすべて `FILE_NOT_FOUND` (404) に丸める。

### 理由

* 正規表現検証をパス結合より前に行うことで、`../` や絶対パスを含む入力がパス操作に到達しない。
* `realpath` の確認は、シンボリックリンクでディレクトリ外を指す場合への対処である。
* 失敗を 404 に丸めることで、ファイルの存在有無を応答から区別できないようにする。

### 影響

* **検証順序を変えてはならない。**正規表現検証を後回しにすると防御が成立しない。
* `fileId` はファイル名のみを符号化する。対象を単一ディレクトリ直下に限定しているため、パスを含める必要がない。

### 関連文書

* `docs/P003-backend-spec.md` §5

## ADR-008

### タイトル

Docker Compose で 2 コンテナ構成として配布する

### 状態

採用

### 日付

2026-08-24

### 決定内容

`web` (nginx、公開ポート 8080) と `api` (FastAPI + sysstat、内部ポート 8000) の 2 サービス構成とする。`api` はホストにポートを公開しない。ログディレクトリは `api` へ**読み取り専用 (`:ro`)** でマウントする。両サービスに `restart: unless-stopped` を設定する。Uvicorn のワーカー数は 2 とする。

### 理由

* ADR-001 の同一オリジン方針を実現するには、静的配信とリバースプロキシを担う層が必要である。
* `api` を非公開にすることで、アクセス経路を nginx に一本化できる。
* アプリはワーカー間で状態を共有しないため (ADR-004)、ワーカー数を増やしても正しく動作する。

### 影響

* **TLS 終端は本構成で行わない。**社内ネットワーク内での利用を前提とする。外部公開時は前段にリバースプロキシを置く必要があり、その手順を配布物の説明に含める。
* ログは両サービスとも標準出力に出し、`docker compose logs` で参照する。
* **本設計を行った環境には Docker が無く、ビルド・起動の確認ができていない。**利用者が最初に `docker compose up -d` → `GET /api/health` で `sadfAvailable` が `true` であることを確認する必要がある。

### 関連文書

* `docs/P005-impl-plan.md` §3 U008 / `docs/P003-backend-spec.md` §13
