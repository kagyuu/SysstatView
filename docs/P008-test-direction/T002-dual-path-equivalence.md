# 【テストID】T002 — 2経路の一致 (観点A)

## 【目的】

* 同一日の `sa` と `sar` を読んだ結果が一致することを確認する (REQ-F-024)。**両対応にしたことで生じた最大のリスクがこの不一致であり、本フェーズの最重要テストである。**

## 【参照テスト計画】

* `docs/P006-test-plan.md` §2 観点A, §2.1 (比較項目と許容誤差)

## 【対象モジュール】

* `readers/sar_text.py` / `readers/sa_binary.py` / `readers/normalize.py`

## 【前提条件】全モジュールビルドが成功していること

* T001 が PASS していること。
* **`sadf` コマンドが利用可能であること。** 利用できない場合は本テストを実行できない。

## 【使用するテストデータ】

* `sa16`〜`sa23` と `sar16`〜`sar23` (同一日の対が 8 組)

## 【事前準備】

* `sadf` の存在を確認する (`shutil.which("sadf")`)。
* **存在しない場合は、本テストを NOT RUN として記録し、その理由 (「この環境に `sadf` が無く導入もできないため」) を明記して T003 へ進む。** スキップとして黙って通過させない。

## 【実行手順】

1. 各日 (16〜23) について `sa{DD}` と `sar{DD}` の `fileId` を取得する。
2. 双方の `GET /api/log-files/{fileId}/metrics` を実行する。
3. 応答同士を突き合わせる。

## 【実行コマンド】

* `python -m pytest backend/tests/integration/test_t002_dual_path.py -q`

## 【期待結果】

対になる 8 組すべてについて、次が一致する。

* `groups[].groupId` の集合
* 各グループの `keyLabel`
* 各グループの `timestamps` (件数と各値)
* 各グループの `series` の `(key, metric)` の集合
* 各 `values` の数値 (**絶対誤差 0.01 以内**を許容する ★FIXME★ 許容値は想定であり、`sadf` の実際の丸め挙動が判明した時点で見直すこと)
* `hostname` / `kernel` / `arch` / `cpuCount` / `date`

## 【合否判定基準】

* すべて一致すれば PASS。1 項目でも不一致なら FAIL。
* `sadf` が無く実行できない場合は **NOT RUN**。**PASS として扱わない。**

## 【失敗時に記録する内容】

* 不一致となった日・`groupId`・`(key, metric)`・両経路の値。
* 差異の性質 (指標名の表記ゆれ / グループの欠落 / サンプル時刻のずれ / 数値の桁違い) を分類して記録する。指標名の表記ゆれであれば `docs/P003-backend-spec.md` §9.3 の対応表の不備であり、修正箇所が特定できるため。
