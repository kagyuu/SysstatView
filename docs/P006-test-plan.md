## 2. 本システム固有の重点観点

本システムは「2 系統の入力を 1 つの内部表現に正規化して描画する」構造であり、テストの重心は通常の CRUD アプリと異なる。次の 3 点を最重点とする。

| # | 重点観点 | 理由 | 担当レベル |
| --- | --- | --- | --- |
| **A** | **`sa` 経路と `sar` 経路の結果が一致すること** | 両対応 (REQ-F-024) にしたことで生じた最大のリスク。片方だけ正しくても要求を満たさない | 結合 (P008) |
| **B** | **`sar` テキストの書式耐性** | 繰り返しヘッダ・`Average:` 行・ブロック分割は、実装が最も誤りやすい箇所 (REQ-F-027, REQ-F-028)。誤ると「それらしいが間違ったグラフ」が出る | 単体 (P007) |
| **C** | **画面状態の復元** | `require.txt` が明示的に求めた要求 (REQ-F-014)。画面遷移をまたぐため単体では検出しにくい | 受け入れ (P009) |

### 2.1 観点 A の検証方法

テストデータには同一日について `sa16`〜`sa23` と `sar16`〜`sar23` の両方が存在する。この対を用いて、両経路の `GET /api/log-files/{fileId}/metrics` 応答を突き合わせる。

比較する項目: `groups[].groupId` の集合 / 各グループの `keyLabel` / `timestamps` / `series` の `(key, metric)` の集合 / 各 `values` の数値。

* 数値の比較は浮動小数点の丸め差を許容する (絶対誤差 0.01 以内) ★FIXME★ (許容値は想定。`sadf` の実出力を確認できていないため、実際の丸め挙動が判明した時点で見直すこと)
* **この観点は `sadf` が利用可能な環境でしか実行できない** (§6.2)。実行できない環境では「未実行」として記録し、合格として扱わない。

## 3. 機能観点のテストケース方針

### 3.1 バックエンド API

| エンドポイント | 正常系 | 主要な異常系 |
| --- | --- | --- |
| `GET /api/health` | 200 / `status="ok"` / `sadfAvailable` の真偽が実環境と一致 / 件数が実ファイル数と一致 | `sadf` 不在でも 200 を返し `status="ok"` のまま (REQ-N-015) |
| `GET /api/log-files` | 期間内の `sa`+`sar` が両方返る / 並び順 (日付昇順→`sa`→`sar`) / 1 ページ 10 件 / `totalItems`・`totalPages` が正しい / 境界日 (`from` と同日・`to` と同日) を含む | `from` 欠落 → 400 / 日付形式不正 → 400 / `from`>`to` → 400 / `page`=0 → 400 / `perPage`=101 → 400 / 総ページ超過 → 200 かつ `items` 空 / 該当 0 件 → `totalPages`=0 |
| `GET /api/log-files/{fileId}/metrics` | `sar` で全グループが返る / `values` の長さ = `timestamps` の長さ / `Average` が混入しない / キー付きグループのキーが正しい / 部分データ (`sa24`) でも 200 | 未知 `fileId` → 404 / 不正 base64 → 404 / `../` を含む `fileId` → 404 / 命名規則外 → 404 / `sadf` 不在 → 503 / `sadf` 異常終了 → 502 かつ同日の `sar` があれば `hint` 付き |
| `GET /api/metric-catalog` | 200 / 18 グループが `displayOrder` 順 / 各グループに `title`・`description` がある / `metrics[]` に `unit` がある | — |

## 4. 非機能観点

| 観点 | 内容 | テストレベル | 合否基準 |
| --- | --- | --- | --- |
| 性能 (一覧) | `GET /api/log-files` の応答時間 (REQ-N-003) | システム (P009) | P95 < 1 秒。テストデータ 18 件 + 生成した増量データで測定 |
| 性能 (メトリクス) | `GET /api/log-files/{fileId}/metrics` (REQ-N-004) | システム (P009) | 初回 P95 < 5 秒 / 2 回目 (キャッシュ命中) P95 < 1 秒 |
| 性能 (キャッシュ効果) | 一覧を連続実行しても採取日の再読み取りが発生しない (REQ-N-016) | 結合 (P008) | 2 回目以降、`sadf` 起動およびファイルオープンが発生しないこと |
| 性能 (描画) | SC-02 の最初のグラフが 3 秒以内 (REQ-N-005) | 受け入れ (P009) | 約 30 インタフェースを含む実データで確認 |
| セキュリティ | パストラバーサル (REQ-N-007) | 単体 + 結合 | `../`、絶対パス、`sa`/`sar` 以外の名前を符号化した `fileId` がすべて 404 |
| セキュリティ | シェル不使用 (REQ-N-008) | 単体 | `subprocess` 呼び出しが配列引数かつ `shell=False` |
| セキュリティ | 読み取り専用 (REQ-N-006) | 受け入れ (P009) | ログディレクトリが `:ro` でマウントされ、アプリが書き込みを行わない |
| 運用 (ログ) | 標準出力への構造化ログ (REQ-N-009) | 結合 + 受け入れ | 1 行 1 JSON。リクエストログに `method`/`path`/`status`/`durationMs` が含まれる。`sadf` 実行が記録される |
| **運用 (再起動耐性)** | **アプリケーションを停止・再起動しても正常に起動すること** | **受け入れ (P009)** | §4.1 参照 |
| 可用性 | コンテナ異常終了時に自動再起動する (REQ-N-010) | 受け入れ (P009) | `restart: unless-stopped` の設定確認 + プロセス強制終了後の復帰確認 |

### 4.1 再起動耐性の観点 (独立した観点として明示)

* 本システムは**永続化されたデータストアを持たず、マイグレーションも存在しない** (P003 §4.1)。したがってマイグレーションの非冪等性による起動失敗は構造上発生しない。
* しかし**再起動そのものの確認は依然として必要**であり、次を確認する。
  * 2 回目以降の起動でもプロセスが正常に立ち上がること。
  * 再起動後、メモリ上のキャッシュが失われた状態から一覧・グラフが正しく再構築されること。
  * 再起動後、`sadf` の有無の検出が正しくやり直されること。
* **この観点は単体テスト・スプリント内結合テスト (P007/P008) では代替できない。** それらはプロセスを起動したまま、あるいはテストごとに新しいプロセス・一時状態で実行するため、「2 回目の起動」という条件を再現しない。したがって **P009 (受け入れ結合テスト) が担当する**。

## 5. テストデータのライフサイクル方針

### 5.1 本システムにおける「テストデータ」

テストデータは `sysstat-log/var/log/sysstat/` 配下の**読み取り専用のログファイル**であり、アプリケーションはこれを一切書き換えない (REQ-N-006)。テスト実行によってデータが累積・変化する経路が存在しない。

### 5.2 ベースラインへ復元する単位

**テストスイートの実行ごと** (既定方針どおり)。

* 具体的には、スイート開始時に「テスト用ログディレクトリが `sysstat-log/var/log/sysstat/` の内容と一致すること」を確認する。
* テストが一時ファイルを作成する場合 (ページ境界を作るための増量データ、破損ファイルの異常系など) は、**元のディレクトリを汚さず、`tmp_path` 配下に別ディレクトリを作ってそこへコピーする。** `SYSSTAT_LOG_DIR` をそのディレクトリに向けてテストする。
* テスト 1 件ごとの復元は行わない。上位ディレクトリを共有しないため、テスト間で干渉が起きない構造になっている。

### 5.3 「ベースライン」が指すもの

**リポジトリにコミットされた `sysstat-log/var/log/sysstat/` の内容そのもの。** マイグレーションも初期データ投入も存在しないため、これ以上の「適用直後の状態」は無い。

### 5.4 テスト間のデータ依存

**許容しない。** 各テストは自身が用いるログディレクトリを自身で用意する (実データを参照するか、`tmp_path` にコピーを作る)。前のテストが作った状態に依存するテストを書かない。

* 本システムは書き込みを行わないため、テスト間でデータ依存が生じる必然性が無い。依存を許容すると、得られるものが無いまま順序依存だけが増える。

### 5.5 スイートの再実行可能性

* **テストスイートを 2 回続けて実行し、同じ結果になることを確認する** (REQ-N-014)。確認は P103・P201・P203・P205 が行う。
* 本システムは永続状態を持たないため 1 回目と 2 回目で条件が変わらないが、**「変わらないはずだ」で済ませず実際に 2 回実行して確認する。** 一時ディレクトリの後始末漏れ、キャッシュを跨いだテスト、生成した増量データの消し忘れなど、実装側の不備でのみ再現する失敗があるため。

## 6. テスト遂行上の技術的な決め事

### 6.1 外部依存のモック方針

| 対象 | 方針 |
| --- | --- |
| `sadf` コマンド | **単体テストではモックする。** `subprocess.run` を差し替え、`tests/fixtures/` に置いた `sadf -j` 出力を模した JSON を返す。異常系 (非 0 終了・`FileNotFoundError`・タイムアウト) もモックで再現する |
| `sadf` コマンド | **結合テスト・受け入れテストではモックしない。** 実際に `sadf` を起動する。`sadf` が無い環境では当該テストを**スキップではなく「未実行」として記録**し、合格に数えない (§6.2) |
| ファイルシステム | モックしない。実ファイル (実データまたは `tmp_path` へのコピー) を用いる。パス解決・`mtime`・`size` の挙動はモックすると意味が失われるため |
| 時刻 (実行月の算出) | フロントエンドの単体テストでは固定日付を注入する。うるう年 (2024-02)、31 日月、30 日月、2 月を検証するため |
| HTTP | バックエンドは FastAPI `TestClient` を用い、実際のネットワークを介さない |

### 6.2 `sadf` が利用できない環境での扱い

**この開発環境には `sadf` が無く、導入もできない** (P005 §5)。`sa` 経路に関するテストの扱いを次のとおり定める。

| テスト | `sadf` 有りの環境 | `sadf` 無しの環境 |
| --- | --- | --- |
| `sa` リーダの単体テスト (フィクスチャ使用) | 実行する | **実行する** (モックのため環境に依存しない) |
| `sa` 経路の結合テスト (実ファイル) | 実行する | **未実行として記録する** |
| 観点 A (2 経路の一致) | 実行する | **未実行として記録する** |
| `sadf` 不在時の 503 応答 | (PATH を汚して再現) | **実行する** (この環境の実態がそのまま条件になる) |

* **「未実行」を「合格」として記録しない。** テスト記録 (P103) には、実行できなかったテストとその理由を明示する。
* `sadf` 不在時の挙動 (REQ-N-015: `sar` のみで動作すること) は、この環境がそのまま検証条件になるため**むしろ確実に検証できる**。この点は制約を利点に転じられる数少ない箇所であり、必ず検証する。

### 6.3 Docker が利用できない環境での扱い

* この開発環境には Docker が無い (P005 §5)。**U008 の成果物 (Dockerfile / nginx.conf / compose.yaml) を実際にビルド・起動する検証は行えない。**
* 受け入れ結合テスト (P009) のうち、コンテナ構成を前提とするもの (可用性・読み取り専用マウント・再起動耐性の一部) は**未実行として記録する**。
* 代替として、バックエンド・フロントエンドを**ローカルプロセスとして直接起動**し、アプリケーション層で確認できる範囲 (再起動後の正常起動、キャッシュ再構築、画面遷移と状態復元) は実行する。
* 何を実行し何を実行できなかったかを P009 のテスト記録に明示する。**できなかったことを、できたかのように書かない。**

### 6.4 テスト実行コマンド

* 各テストレベルの実行コマンドは P007 / P008 / P009 に記載する。
* **記載する前に必ず一度実際に実行し、意図したテストが実際に実行されること (パス指定の誤りで 0 件が静かにスキップされていないか) を確認する。** 実行して確認していないコマンドを、動作確認済みであるかのように記載しない。

### 6.5 テスト記録

* 結合テストの実行記録は `docs/test-records/YYYYMMDD-HHMM-test-record.md` に残す (P103 / P205)。
* 記録には、実行したテスト数・合格数・失敗数に加えて、**未実行のテストとその理由**を必ず含める。
